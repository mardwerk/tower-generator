# Bounded Unit mechanics

This is the contract of the current numerical Engine (`src/cli/internal/mechanics`): three paths of five tiers. Shared forms, stamina, Apex purchases and other progression shapes are not supported and need an explicit Engine change. Every draft follows the one generation route in [ARCHITECTURE.md](ARCHITECTURE.md#generation-route).

The mechanics module resolves purchased Unit builds and checks their declared behavior. It does not simulate combat, waves, travel, enemy layers, map geometry, runtime cooldowns or balance. Its explicit Definition is a small, experimental combat vocabulary inspired by ordinary BTD6 towers; [BTD6 facts](BTD6-REFERENCE.md) live in btd6-atlas. It does not reproduce BTD6's numerical balance or complete damage table.

BTD6 tower data, whether the retired 26-tower dataset or btd6-atlas, is reference data, not a loadable mechanics Definition. It distinguishes a supported operation's shape from missing numerical values, unspecified behavior and unsupported operators. No advisory label can authorize a mechanic or fill a missing value.

## Source-backed starter authoring

Every draft is planned first. A first model stage plans the source-backed repertoire, base attack, three purchasing reasons and branch milestones. A second stage implements the plan using the supported mechanics. Code binds the retained plan's names and evidence, resolves numerical operations and validates every legal build. `run.designPlan` preserves the plan; attempts distinguish `plan`, `design` and `repair`. Each stage permits one repair by default. A draft that still fails keeps its evidence: every attempt's issues and rejected output, the plan once one was accepted and the source passages the model was given. The CLI writes it beside the requested output (`dart.json` → `dart.failure.json`), the API returns it as `error.evidence` and the web app offers it as a download. Source selection is bounded to 200 passages and 32,000 characters, and source text remains evidence rather than instructions.

New plans also declare `upgradeIntents` for each path and tier. Each intent lists promised improvements, such as damage, attack rate or active duration, a supported unlock when needed, the technique the purchase adapts, and `lowers`: tradeoffs the description states, such as the attack rate of a slower, heavier attack. After mechanics validation, the compiler compares those promises with resolved purchases across legal builds. A range-only upgrade cannot fulfill a promised damage increase, and a promised tradeoff must lower its dimension in every legal build that contains the purchase. A broken promise names the change that keeps it. Improvements without the `active-` prefix are permanent; the boost's own multipliers never keep them. A mismatch enters the existing bounded repair; it adds no separate model call. The same check runs when checking a saved draft, so changing its mechanics cannot silently discard its retained promises. These checks verify the selected dimensions, not the meaning of every sentence, fair prices or character fidelity. Older saved plans without intents remain readable. An unsupported source aspect a purchase needs is a proposed mechanic of that milestone (`proposedMechanics: [{name, effect, sourceIds}]`, at most two); code binds each to its purchase in the mechanics output, and `check` fails a saved draft whose purchase no longer carries one (rule `planned-upgrade-intent`). Other unsupported aspects stay explicit omissions.

Edited requirements and revisions use the same route. Older artifacts may name `profile.authoringMode` (`planned-v1`, `direct` or `reference-patterns-v1`); the field is kept for reading and no longer selects a route. Historical linked skills retain their source qualifier and an explicit source-period decision. The route does not prove exhaustive character coverage or gameplay balance.

The bundled Definition and Profile are built into the binary: `mardwerk-unit definition` prints the Definition, and a saved Profile is an edited copy. The shared default cannot be edited in place.

## Default authoring policy

The bundled Profile (`default`) and `definition` use the authoring Definition `2026-09-27-atlas-56.3-v28`, a [version 2 Definition](#profile-defined-vocabulary-version-2) whose vocabulary names the starter's slow, burn, stun, damage types, targeting and Camo detection, plus Knockback and the Hardened enemy property; Hardened and Blimp, two separate properties, accept [bonus damage](#bonus-damage), and it otherwise behaves exactly as the version 1 starter. Its rules document is `default-td-profile-v28`; its scale references come from btd6-atlas ([BTD6 reference](BTD6-REFERENCE.md)). A second read-only Profile, `stacking-example`, adds stacking poison and bleed. Its optional `profile.designPolicy` adds design gates to the existing combat DSL. Previously saved and custom Definitions without this field retain their original validation; the policy-free combat baseline (`mechanics.DefaultDefinition`, revision `2026-09-20`) is the base the Default Definition extends; the kit sheet and stats fall back to it only for a candidate that carries no Definition.

Purchases are named by build code, top-middle-bottom: `0-0-0` is the base Unit, `1-x-x` to `5-x-x` the top path, `x-1-x` to `x-5-x` the middle path and `x-x-1` to `x-x-5` the bottom path; `x` means unspecified, and `3-1-0` is a concrete build. `path1`, `path2` and `path3` in the contract are the top, middle and bottom paths.

- Every path declares a `specialization`: `direct-damage`, `group-damage`, `attack-speed`, `control`, `range` or `ability-burst`. Broad specialties may repeat when purchasing reasons differ. The default preserves basic-attack identity through the first and second purchase, and what those purchases improve belongs to their path (`exclusiveEarlyBenefits`, below). The third purchase defines the path, or at least distinguishes it: it improves, unlocks or proposes something no purchase of the other paths does (`requireTier3PathIdentity`, below). The identity can be simple, as Dart Monkey's `0-3-0` Triple Shot is the only Dart Monkey purchase with more than one projectile, or a new form, as Mermonkey's `3-0-0` Abyss Dweller adds tentacle attacks. The fourth develops that identity, and the fifth is the pinnacle of the path: beyond larger numbers it adds a supported behavior or a proposed mechanic (`requireTier5BehaviorChange`, below), as Mermonkey's `5-0-0` Lord of the Abyss also creates water around itself. Not every purchase needs a new mechanic. From the third purchase on, a purchase that raises damage also changes how the attack reaches or affects enemies, such as pierce, attack rate, a status, bonus damage against an enemy property or the Active Ability; more range alone does not count, and the review flags a third, fourth or fifth purchase whose typed changes only raise damage. The model review judges significance and the progression; code rejects changes with no effect, such as a distinct-target volley of one projectile.
- Code judges no payoff. The plan check (`PlanFeasibilityIssues`) rejects promises the mechanics could not keep: an active promise without the same path's boost, a capability unlocked twice on one path and promises beyond the change budget. Under `exclusiveEarlyBenefits` or `distinctEarlyBenefits` it also rejects early benefits two paths share, and under `requireTier3PathIdentity` and `requireTier5BehaviorChange` a third purchase without an identity and a fifth purchase without a behavior or proposed mechanic (below). The promise check then requires every promised dimension to improve in every legal build, also when a saved draft is checked, and validation rejects changes with no effect. Whether a fourth or fifth purchase pays off, or raises damage too little for its price, is still the review's judgment from the resolved purchase evidence.
- Every plan milestone names the `technique` it adapts: the base attack or a repertoire entry, exactly as the plan names it. Under a design policy code checks these typed techniques, not purchase or Active Ability names (`PlanTechniqueIssues`). Every path must adapt a repertoire technique no other path adapts, its identity. Two paths may adapt the same technique as crosspath synergy only in purchases that a legal build owns together, so one of them is a first or second purchase; a technique split between purchases that never meet, such as a middle-path Active Ability boosting a form the top path reaches at `3-x-x`, is rejected. Plans saved before the field existed are not checked.
- Every repertoire entry lists its `effects`: what its cited passages describe the technique doing, one per item, such as greater strength and greater speed for a form that raises both. Each effect is adapted as the promises in `adaptedAs`, such as `damage` and `attack-rate`, or, with `adaptedAs` empty, omitted; its `reason` says how or why. Code checks every adapted promise, in its plain or `active-` form, against the `improves`, `unlock` and `lowers` of the purchases whose technique is that entry (`PlanEffectIssues`), for every Definition; the promise check then holds those purchases to typed changes. Only entries that purchases adapt are checked: an entry named like the base attack is shown by `0-0-0`, and an entry no purchase adapts should omit every effect. The review sees each entry's `adaptedBy`, the purchases code found for it, and fails an adaptation claimed by an entry no purchase names. Code does not check the reverse direction, that each promise of a purchase is an adapted effect of its technique: in the 16 saved v20 Luffy plans 80 of 436 such promises are not, and the scripted Dart Monkey has several, so a gate would reject nearly every plan. Instead each purchased tier in the review context lists them as `promisesWithoutEffect`, and the review fails an adaptation or name that credits the technique with one unless a passage the technique cites describes it. Whether the list covers the passages, and whether an omission's reason holds, is the review's judgment. A milestone may promise up to five improvements; the change budget bounds what it can keep. Plans saved before `effects` existed load and render unchanged and are not checked.
- A stat-led path is allowed. The review judges whether its third purchase and capstone give a substantial payoff, from `purchaseEvidence`: the resolved comparisons of each path's third, fourth and fifth purchases and its crosspaths. The review also receives `legalBuilds`, every legal build with its resolved price, attack and Active Ability, so it reads hit counts and crosspaths instead of recomputing them; its mismatch findings cite resolved values that code checks, and a review citing an illegal build or a wrong value is corrected once, then rejected; the correction must return the findings whose citations held. Two readings are derived from the retained evidence whenever it is read, for the review and `render --details`, and are not saved: next to an Active Ability's peak and duty fraction, the time-averaged direct and group rates, `peak × duty + ordinary × (1 - duty)` with duty `min(1, duration / cooldown)`, which assume activation whenever ready and equal the ordinary rate without an Active; and for each crosspath purchase, `againstCapstone`, its absolute time-averaged direct and group gain and its price beside the same of its main path's own fifth purchase (`4-0-0` to `5-0-0` for the top path), such as "side `1-x-x` adds +1.05 direct for 140; the path's `x-x-5` adds +12.64 for 45,000", with `sideGainAtLeastCapstone` stating whether the side gain is as large as the capstone's or larger. The review's `purchaseComparisonOrdering` orders each fifth purchase against the same-budget copy bound by the ordinary and the time-averaged direct and group rates, each copy owning the fourth purchase's Active Ability, and sets `activeOnly` when every typed change of the fifth purchase changes the Active Ability; such a capstone's ordinary ratio is the same as for one that adds nothing, so the review states its time-averaged ordering and whether its typed changes deliver the plan's `capstoneValue`, and reports it as unresolved when they do not. This is a checked comparison, not a balance verdict. A finding that states the opposite of the one `againstCapstone` comparison its quoted numbers identify is corrected like a wrong fact ([architecture](ARCHITECTURE.md)). Prices are in the Definition profile's `currency`, such as Gold, which the review guidance and the derived limitation name. No gain is divided by a price: a cheap side purchase almost always wins a per-currency ratio, so such a ratio says nothing about the capstone. Both readings are evidence for the review, not a gate or a finding. The review also receives `referencePrices`, which states each path whose five incremental prices equal the Definition profile's `referenceScale.incrementalUpgradeCosts` exactly. The mechanics prompt asks for prices derived from this Unit's payoffs by value rather than a copied reference sequence, and the review judges whether each fourth and fifth purchase's price fits its time-averaged gain and whether the capstone keeps a reason to buy. It compares absolute gains and prices, counts a side purchase against the capstone only when that cheap purchase adds as much absolute gain or more, and never uses a per-currency ratio as capstone evidence by itself. Neither is a gate.
- Under `distinctFirstUpgrades`, resolved first purchases must differ between paths. Renaming, repricing or writing equivalent add/set/multiply expressions does not evade the check. Pure `5-0-0`, `0-5-0` and `0-0-5` builds must also differ after removing names and costs (`distinctCapstones`).
- Under `distinctEarlyBenefits` (#32): two paths' first two purchases together must differ in what they improve or unlock, whatever their order, names, prices or amounts; lowers do not count. A path's early benefits are the multiset of its first and second purchases' improvement dimensions and unlocks: order is ignored, a dimension both purchases improve counts twice, and `lowers`, names, techniques, prices and amounts are left out. Range then damage on `x-1-x` and `x-2-x` therefore repeats damage then range on `x-x-1` and `x-x-2`, while an added improvement or a distinct unlock makes a path distinct. Third purchases are not included. Two checks apply the rule:
  - The plan check rejects the later of two matching paths at its second milestone, naming both paths and the shared benefits, and the plan goes through the existing bounded correction before any mechanics call.
  - The resolved check (`EarlyBenefitsIssues`) compares the pure builds `0-0-0` to `2-0-0`, and the same for the middle and bottom paths, with the promise check's measures, so a change the plan does not promise can still make two paths match. It runs beside the promise check in drafting and in `check` (rule `distinct-early-benefits`), not in rendering. Its issue names both paths and each path's resolved early benefits, then targets the purchase whose resolved benefits depart from the retained plan, says which benefit caused the match and asks to make the early benefits distinct while keeping that purchase's promises; `TargetedTierRepair` rebuilds that tier within the repair budget. It is not a general rule against unpromised changes.
  - The plan prompt, the draft and repair guidance and both issues carry the same rule sentence. Definitions without the field, including saved and custom Profiles made before it, are not checked.
- Under `exclusiveEarlyBenefits`, which the Default enables from v27 (#61): no dimension or capability that one path's first two purchases improve or unlock may be improved or unlocked by another path's first two purchases, whatever their order, names, prices or amounts; a path may repeat its own, any path's third to fifth purchases may improve it, and lowers do not count. When `1-x-x` adds damage, `x-1-x`, `x-2-x`, `x-x-1` and `x-x-2` add none; a second damage purchase belongs on `2-x-x`. Dart Monkey's middle path attacks faster twice, which is allowed within one path, and a later purchase such as `x-3-x` may add damage beside its own dimension. The same unlock on two paths' early purchases is shared too, such as personal Camo detection at `2-x-x` and `x-x-2`: two paths that both open it early give a crosspath nothing twice, as two paths that raise the same stat do. An unlock of a dimension a purchase can also improve, such as splash, a status effect or bonus damage, counts as that dimension, and a targeting change counts as nothing. The rule subsumes `distinctEarlyBenefits`: early benefits that share nothing differ, since every early purchase improves or unlocks something. With both fields set only the exclusive rule is stated and checked, and a saved Profile that sets only `distinctEarlyBenefits` keeps the multiset rule. It has the same two checks, with the same targeting of the purchase that departs from the retained plan: the plan check names the later path's milestone that promises the shared benefit, and the resolved check runs in drafting and in `check` (rule `exclusive-early-benefits`), not in rendering.
- Under `requireTier3PathIdentity`, which the Default enables from v27 (#61): the third purchase of every path must distinguish it: it improves or unlocks a dimension or capability, or carries a proposed mechanic, that no purchase of the other two paths improves, unlocks or proposes; lowers, names, prices, amounts and a targeting change do not count. "The other paths' purchases" are their own purchases `1` to `5`, not crosspaths. Improvements and unlocks are compared as `exclusiveEarlyBenefits` compares them, and a proposed mechanic by its name, ignoring case and spacing. The benefit need not be new to its own path, so Crossbow-style range on a path whose early purchases raise range counts when no other path raises range; larger numbers may come beside it. Dart Monkey's `x-3-x` passes because no other path adds projectiles. The plan check reads the milestones' promises and proposed mechanics; the resolved check (`PathIdentityIssues`) compares every path's pure builds, so an unpromised change on another path can take a third purchase's identity. With a retained plan it targets that purchase, or the third purchase when it drops its planned identity, for `TargetedTierRepair`. It runs in drafting and in `check` (rule `path-identity`), not in rendering. The review judges whether the identity is a real one. BTD6's own Dart Monkey would not pass as captured, because `3-0-0` Spike-o-pult also raises range (32 to 36.8) while `0-0-3` Crossbow raises only damage, pierce and range; the scripted fixture adapts Spike-o-pult without that range and proposes its rebound as a mechanic.
- Under `requireTier5BehaviorChange`, which the Default enables from v27 (#61): the fifth purchase is the pinnacle of its path. It must add a supported behavior or access (`HasBehaviorTransition` over the pure fourth purchase) or carry a proposed mechanic; larger existing numbers, the Active Ability's included, do not count, so an Active-only capstone that only raises the Active's multipliers, duration or frequency fails, while one that adds an active follow-up passes. The plan check applies it to the fifth milestone's promises and proposed mechanics, and the resolved check to the pure builds. The review fails a proposed mechanic that only restates larger numbers or does not make the purchase the pinnacle of its path. A targeted repair of an earlier tier includes the fifth purchase only when that tier could add the same behavior: a third or fourth purchase, or a first or second one without early identity, and never when the fifth purchase carries a proposed mechanic.
- Under `requireCoreConcepts`, which the Default enables from v28 (#61): rank every repertoire entry and every omitted technique core, major or minor, and list every source technique in the repertoire or in omittedTechniques; one to three entries are core, the concepts without which the character would not feel canonical, and each core entry is the base attack or the technique of at least one purchase that adapts its central effect with a typed change, and is never omitted whole, only in named aspects; a core entry adapted only by a proposed mechanic is an unresolved design gap, because a proposal grants no behavior, and the Unit embodies it only once the Definition supports that mechanic. Each repertoire entry and omitted technique carries `importance` (`core`, `major` or `minor`), and the plan judges it from the sources: a [source technique](../CONTEXT.md)'s signature flag, how much of the power sections it occupies and what the character is known for. Ideally the core entries define the paths, one path's identity each; generation chooses freely among major and minor entries. The plan check (`CoreConceptIssues`) runs only for a request that lists its `sourceTechniques`, as `prepare` has made since #65, and checks presence and naming only: every entry is ranked, one to three are core, a purchase names each core entry as its `technique` (a core entry named like the base attack is adapted by `0-0-0`) and adapts it, with a promise that one of the entry's `effects` is adapted as (any promise when the entry lists no effects) or with a proposed mechanic on its milestone, no omitted technique is core or is named for a core entry (as a source technique is listed by name, below), and every source technique is listed. A source technique is listed when the base attack, a repertoire entry or an omitted technique is named for it: the names have the same words, ignoring case, punctuation, parentheses and a trailing "Techniques", or the entry's name adds only the words form, mode, technique, transformation, attack or move, singular or plural, as "Gear 4 forms" lists "Gear 4". Any other added word makes a different concept, so a generic entry never lists a more specific technique ("Haki" lists neither "Armament Haki", "Observation Haki" nor "Supreme King Haki") and a specific one never lists a generic one. Citing a passage lists a technique only through a form: the base attack or a repertoire entry named for a source technique that is a form lists another source technique when it cites a passage of that technique whose section path has the form as a heading and names the technique below it, as a lower heading or the passage's leading term, as a Gear 4 entry citing "Python (…): …" under "Devil Fruit > Gear 4" lists Python. A Pistol entry citing a Gear 4 passage lists neither Gear 4 nor its attacks, and a generic entry lists no more specific technique by citation either (SOL-67-01). `check` then reports each core entry that the Unit does not embody (rule `core-concept`): none when a purchase whose technique it is promises what one of its effects is adapted as, an unresolved Finding when only proposed mechanics on those purchases adapt it, since no build grants a proposal, and a failure when they adapt it with neither. An omitted aspect of a core entry, such as "Gear 4 flight" beside a core "Gear 4", is allowed. Whether a purchase fulfils the concept's spirit is the review's judgment (`unit.CoreSpiritRule`): a purchase adapts a core concept only when its typed changes or proposed mechanics do what the concept does in play, not when it only carries the concept's name: a summoning concept adapted only as more range does not fulfil it; a summoned unit, an added attacker or a spawned helper would. Code judges no prose, since prose heuristics produced false positives (SOL-57-01). The review also fails a ranking the sources contradict. Saved plans without `importance` load, render and check unchanged, and a request prepared before `sourceTechniques` is not checked.
- Every whole technique in `omittedTechniques` follows one rule (`unit.OmissionRule`), which the plan prompt states and the review applies whatever the policy: a whole technique in omittedTechniques names in its reason the exact effect the Definition cannot express, and an effect a purchase needs goes on that purchase as a proposed mechanic instead; a reason does not hold when a supported promise expresses the effect, as a sudden speed increase is attack-rate, a blow that sends enemies flying is a knockback status and damage that reaches enemies other attacks cannot hurt is a damage type or bonus damage. A reason is not enough by itself: the review judges each reason against `definition.vocabulary` and fails one that does not hold, as the v25 Luffy plan's reasons for omitting Gear 4, Gear 5 and Armament Haki would fail (OPUS-NET-61-1). The review no longer exempts a core entry from "every source ability".
- At most one path may unlock a manual boost, defaulting to `path2`, the middle path, at `x-4-x`. Optional `manualAbilityPath` can select a different path; `null` forbids boosts, and omission retains the older count-only check. A `maxManualAbilityPaths` of 0 forbids them on every path, whatever `manualAbilityPath` says, and the prompts then say that no path may have an Active Ability. This follows the atlas pattern (a middle-path fourth-purchase ability in 25 of 26 towers), not a universal BTD6 restriction.
- The boost is the only Active Ability the Definition expresses: a temporary change to the purchased attack. `x-5-x` may modify that same boost. A design that asks for a second `x-5-x` Active, a ground-targeted strike or a separate Active attack must fold the fifth purchase into a modification of the boost or record the extra Active as an unsupported mechanic; the Definition has no second button.
- Optional custom policies can require distinct specialty labels, a third-purchase behavior transition (`requireTier3BehaviorChange`, checked in the plan and the resolved builds like the fifth-purchase rule, and met by a proposed mechanic too), or a `minTier5SpecialtyMultiplier` on an established positive fourth-purchase metric. The default leaves these gates unset: its third purchase needs an identity, not a new mechanic. Failed checks enter bounded repair and never silently change stats.
- Each design policy field's rule is one sentence in `mechanics/policy_text.go`. The plan prompt and the draft and repair guidance state it only while the field is set, and every plan, promise and resolved failure of the field carries it verbatim: first the failure's facts, such as "Resolved 2-x-x adds burn and changes targeting.", then the rule, then the fix. The early-identity rule names everything its checks reject: a new status, splash, follow-up or distinct-target volley, a new delivery, targeting or damage type, and a second projectile on a single-projectile attack. `requireTier5BehaviorChange` states its rule in the plan prompt and the guidance, as `requireTier3BehaviorChange` does. `exclusiveEarlyBenefits`, `requireTier3PathIdentity` and `requireCoreConcepts` each have one sentence as well, and so do the rules the prompts and review state without a policy check: the naming rule, the omission rule and the core concept spirit rule (`unit/prompt_text.go`). `unit/policy_wording_test.go` pins every sentence, so a wording change is deliberate.

Purchase names follow one naming rule (`unit.NamingRule`), which the mechanics prompt states and the review applies: a purchase is named for what it does, with the source's own name for what it adapts, even when that name suggests something else, as a punch the source calls a pistol keeps that name; where no source name fits, a descriptive word, such as Reach or Quick, that matches its typed changes or proposed mechanics. A name that borrows a source concept for a different effect, such as Farseeing Reach on a purchase that raises range and pierce, fails review on that build code, with the replacement name in the finding's action. Code judges no name. The review's in-call correction repairs only its own citations, so the failed finding is published and listed under Corrections needed; a revision (`edit`) carries it as `previousFindings`, and the mechanics prompt asks a revision to rename the purchase as that action says.

Behavior the Definition cannot express stays on the purchase that needs it as a [proposed mechanic](../CONTEXT.md): a tier's `proposedMechanics` lists `{name, effect, sourceIds}`, where `effect` says concretely what it does in play and `sourceIds` cite source passages, beside the typed changes that approximate it. A tier still needs at least one typed change, and build resolution ignores proposed mechanics, so they change no stat and no build grants them. Each one becomes an unresolved deterministic finding with rule `proposed-mechanic` and category `unsupported` that names the purchase and says the Definition must be expanded before it can be granted. The review judges whether each fits its purchase and cited passages and fails one that is lore rather than a playable mechanic. The unit sheet shows each on its purchase as "Proposed (not yet supported)"; crosspath rows leave them out. Tiers saved before proposed mechanics existed have none. Behavior that belongs to no purchase is listed as `proposals` in the blueprint (`unsupportedMechanics` in model output). Each one becomes a `proposed_extension` mechanic and an unresolved deterministic finding with rule `unsupported-mechanic` and category `unsupported`: no build grants it, and no name or sentence can. Checked artifacts made before this rule carry the older `declared-mechanic-support` finding for proposals; run `check` on their draft again before reviewing them.

Direct damage rate is `damage × primaryProjectiles / interval + burnDamagePerSecond × min(1, burnSeconds / interval)`, where a distinct-target volley contributes at most one projectile to the primary enemy. Group capacity includes the declared distinct targets, pierce and bounded secondary hits. Attack speed compares `1 / interval`; range compares reach. Control compares slow percentage or stun uptime, capped by refresh intervals and multiplied by pierce. Ability burst compares the boosted attack's peak direct/group capacity or `duration / cooldown`. A duty-only ability gain must also retain peak output. Group/control values are idealized upper bounds, and active availability assumes useful activation timing. No metric models enemies, immunity, projectile travel, map coverage, allied support or real wave damage. A zero or nonfinite T4 metric cannot satisfy a ratio gate. Different labels and passing ratios still need semantic review for coherent paths, weaknesses, price and canon fidelity.

`tier5Uniqueness: one-per-player-unit-type-and-path` records the deployment contract: one T5 of a given type and path across that player's placed copies, with different paths permitted on separate copies. This is distinct from one copy's crosspath legality. The generator has no roster state and cannot enforce scene ownership; the consumer must implement it. Support, income, new actors and access-based capstones outside the current vocabulary require explicit extensions rather than invented damage to pass a proxy gate.

These conventions were first drawn from the retired September 20 pattern analysis and now follow the btd6-atlas 56.3 progression patterns ([BTD6 reference](BTD6-REFERENCE.md)). [PROFILE-EVALUATION.md](PROFILE-EVALUATION.md) records how a Dart Monkey generation under this policy compared with the atlas. A historical [bounded-search proposal](https://github.com/mardwerk/unit-generator/blob/01000bf/research/AUTORESEARCH.md) described candidate search and independent evaluation; autonomous search is not implemented or run by default.

Targeted repair preserves unrelated tiers and includes dependent capstones in the same model call. Under a policy with a fifth-purchase gate, repairing the first to fourth purchase also includes that path's fifth so its relative payoff can be corrected. When the fourth purchase is repaired and the fifth modifies its boost, the fifth is included too. Dependent capstones require complete replacements, including valid prerequisites; the default budget remains one repair.

The Go package `src/cli/internal/mechanics` is the entry point. `BlueprintSchema` and `MechanicsDefinitionSchema` are strict schemas. `ValidateBlueprint(blueprint, definition)` returns structured `{path, message}` issues. `ValidateTyped` is the same check on typed values. `ValidateStructure` runs only its structural part ([below](#checks-and-limits)). `ResolveBuild(blueprint, Selection{path1Tier, path2Tier, path3Tier}, definition)` rejects a blueprint whose structure is invalid, or an illegal selection, with a `ValidationError` whose `Issues` retain those locations. `AllLegalBuilds(definition)` lists permitted selections. `DefaultDefinition()` returns a fresh copy of the baseline each call. The CLI exposes resolution as `mardwerk-unit build ARTIFACT --tiers A,B,C`. No filesystem, model, network or hidden project state participates in resolution.

## Inputs and supported vocabulary

A `UnitBlueprint` names the Unit, its role and weakness, and contains one `baseAttack`, three required named paths, proposals, reserved techniques and constraint coverage. One to eight `sourceFacts` preserve a supplied document ID and quote. Each path names its theme, gives a short rationale and references at least one existing fact by zero-based `sourceFactIndices`. Source indices are checked here; verifying that the quote actually appears in the supplied document belongs to the evidence boundary. `constraintCoverage` records `{constraintId, implementation}` entries for explicit caller constraints. Descriptive prose is not executable behavior or evidence that a constraint has been satisfied.

The compiler derives the visible role, path summaries and tier benefits from resolved mechanics. Original model role, weakness, theme and rationale are retained as unverified authoring notes in the blueprint. The provider-facing format is smaller than this DSL: models select source passage IDs, and code builds the fact indices. Models author slow and burn as complete magnitude/duration pairs. These choices reduce malformed output without changing the saved mechanics contract.

Paths use the required object keys `path1`, `path2` and `path3`. Every path supplies required `tier1` through `tier5` keys. An upgrade has a name, positive incremental cost and at least one typed change. The Definition sets the change budget: a version 1 Definition allows at most four, and at most three in its early tiers (T1 through T3 in the policy-free baseline); a version 2 Definition may allow up to eight. The Default Definition allows three changes at T1 and T2 and five from T3. A legal build includes every preceding tier on each selected path. The default permits at most two purchased paths. Buying T3 commits that path as the main path: the other purchased path may still buy T1 and T2, but cannot buy T3. The third path remains unavailable. If no secondary path has been purchased yet, either remaining path can fill that slot through T2. There are exactly 64 builds: the base, 15 single-path builds and 48 two-path builds. This includes `2-2-0`, all six fully developed crosspaths and intermediate purchases. Neither `3-3-0` nor `1-1-1` is legal.

Under a version 1 Definition, the base attack has a name, positive purchase cost, delivery (`projectile`, `instant`, `area` or `beam`), damage type (`sharp`, `normal`, `explosive` or `energy`), target priority (`first`, `last`, `close` or `strong`), a Camo detection flag and the following numeric stats. A version 2 Definition keeps the first six stats and takes the rest from its [vocabulary](#profile-defined-vocabulary-version-2):

| Stat | Contract |
| --- | --- |
| `damage` | Nonnegative direct damage per hit. Zero is allowed for an attack that supplies control or burn. |
| `intervalSeconds` | Positive seconds between ordinary attacks or beam pulses. |
| `range` | Positive maximum target distance in the supplied game scale. |
| `pierce` | Positive integer maximum distinct enemies affected by one projectile or pulse, including its splash. |
| `projectiles` | Positive integer number of projectiles or pulses produced by one attack cycle. |
| `splashRadius` | Nonnegative radius around the impact target. Area delivery requires a positive radius. |
| `slowPercent`, `slowSeconds` | Slow percentage from 0 to 100 and nonnegative duration. Both must be positive together or both zero. |
| `burnDamagePerSecond`, `burnSeconds` | Nonnegative burn rate and duration. Both must be positive together or both zero. |
| `stunSeconds` | Nonnegative stun duration. Zero disables stun. |

Delivery selects the declared attack shape. Projectile travel and beam geometry are not simulated. A beam remains a periodic attack, not a second clock. Target priority selects the first enemy along the route, last enemy, closest enemy or strongest eligible enemy. Tie resolution, collision paths, distance measurement and enemy ordering require a runtime implementation. `pierce` limits one projectile's target count; it is not armor penetration. Without an extension, every projectile aims at the same selected primary target and separate projectiles may each hit it. A projectile can affect a given enemy at most once. Pierce includes its primary and splash recipients together; a positive splash radius requires pierce of at least two. Travel and collision still belong to the host.

The bundled authoring Definition retains the earlier extensions and explicitly enables `distinct-volley` and `volley-follow-up` in `rules.attackExtensions`. These extensions are optional for older Definitions:

- `distribution: "distinct-targets"` assigns one initial shot per eligible enemy, primary first, then nearest to that primary with stable ID tie-breaking. Unused shots are lost; they do not concentrate on the primary. Omission or `"same-primary"` retains the original volley.
- `followUp: {name, count, damageMultiplier, radius, inheritStatuses}` emits at most `count` secondary hits once after a primary volley hits. Each hits a different eligible enemy within the selected primary impact's radius and excludes every enemy already hit by the volley. Direct damage derives from purchased hit damage; statuses inherit only when declared. Secondary hits neither recurse nor multiply through pierce, splash or projectile count.

The host implements this selection from its own geometry: distance is measured from one selected primary impact even when a volley targets several enemies, secondary delivery requires unobstructed impact-origin geometry, and detection and immunity still apply. The Tool resolves the declared counts and multipliers; it does not select targets, simulate trajectories or collisions. Multiplying idealized target capacities does not establish measured wave damage. (The TypeScript Tool shipped helper functions for this selection; they were not ported, because the Go Tool has no runtime consumer.)

Ordinary changes explicitly target `base`. A `followUp` change may target `boost` to affect only the same path's owned manual ability. Numeric changes use `{kind: "stat", target: "base", stat, operation, value}`, with `operation` equal to `add`, `multiply` or `set`. Typed `camo`, `damageType`, `delivery`, `targeting`, `distribution` and `followUp` changes set their matching `value`. No change can target a nonexistent attack, summon or aura. The supported attack remains one loop, even when its delivery changes.

A path may unlock one manual boost at tier 4 using `{kind: "unlockBoost", target: "base", boost}`. The boost requires a name, positive duration, positive cooldown, positive damage multiplier, positive interval multiplier and nonnegative range bonus. Its duration cannot exceed its cooldown. At tier 5, `{kind: "modifyBoost", target: "base", stat, operation, value}` can modify a numeric field of that same path's tier 4 boost. There is no crosspath reference or second button. A boost-targeted follow-up requires that same path's T4 boost and is resolved only while it is active. Early tiers cannot unlock or modify a manual boost.

Summons, separate automatic weapons, ally support, teleports, transformations with independent state, economy, terrain changes and conditional triggers are unsupported. Put a requirement a purchase needs in that tier's `proposedMechanics: [{name, effect, sourceIds}]`, one that belongs to no purchase in `proposals: [{name, reason}]`, and preserve unused source techniques in `reservedTechniques: [{name, reason}]`. These arrays can be empty. None of them executes or silently grants the named behavior. Changing the Definition cannot implement a new operation outside this vocabulary.

## Resolution and inheritance

For each numeric stat, resolution selects the last purchased `set` as its baseline, or the base value when there is no setter. It then adds all purchased `add` values and multiplies by all purchased `multiply` factors:

```text
resolved = (baseline + sum(additions)) * product(multipliers)
```

Changes have a canonical order: ascending tier, ascending path number, then their order inside the upgrade. Therefore the highest-tier setter wins, with later path and change indices breaking ties. Setters replace the baseline only; they do not erase purchased additions or multipliers. Boolean and enum setters use the same last-wins canonical order. There is no purchase-order input, so identical builds always resolve identically. Validation reports an upgrade that becomes ineffective in any legal combination, including a setter erased by another path.

For example, base damage 10, a secondary-path `add 2`, a main-path `set 20` and `multiply 2` resolve to damage 44. The setter preserves the secondary purchase. A tier 5 boost damage multiplier of 3 then produces active damage 132. Ability resolution applies its final parameters to the fully resolved purchased base attack, preserving secondary-path detection, damage type, pierce, projectiles and status effects. Boosts change direct damage, attack interval and range only; they do not multiply burn rate, control duration or their own cooldown. Every activation must improve actual damage, attack interval or range over the purchased permanent attack, even if its unlock also grants a permanent benefit. Mixed benefits and drawbacks remain allowed.

An owned ability is initially ready when purchased. Activation starts its cooldown and applies its temporary boost for its duration. It cannot reactivate while active. The temporary state ends at duration expiry, and readiness returns after cooldown expiry. Boosts do not stack. The resolver reports ownership, `initiallyReady`, declared timing and the attack while active; it does not pretend to know current runtime readiness. Tier 5 modifies the existing ability contract rather than adding another activation.

The result includes `selection`, the permanent `baseAttack`, owned `abilities`, `cumulativeCost` and `tierDeltas`. Each delta includes its path, tier, name, incremental cost, cumulative cost, declared changes and the before/after permanent attack. Deltas use the same canonical tier-first purchase order. Cumulative cost adds the base purchase and every preceding upgrade on the selected paths exactly once. It excludes every unpurchased tier. An ability-only upgrade can have equal before/after permanent attacks while still adding meaningful behavior in `abilities`.

## Detection, resistance and control

Camo detection grants target access only. Every supported delivery requires a clear path, including instant, area and beam attacks. Neither Camo nor damage type grants obstruction bypass.

The starter taxonomy uses the properties `lead`, `frozen`, `purple`, `black`, `zebra`, `blimp` and `boss`. Sharp damage is resisted by Lead and Frozen, explosive damage by Black and Zebra, and energy damage by Purple. Normal has no immunity in this limited table. Damage immunity gates both direct damage and burn from the attack. These names provide a simplified authoring taxonomy, not the complete BTD6 damage system or a claim that Normal bypasses armor, shields, boss mechanics or every possible restriction.

Control eligibility is separate from damage eligibility. The starter excludes Blimp and Boss properties from slow and stun. For example, an explosive attack may apply a declared slow to a Black target while its damage is resisted. Detection and obstruction still gate both damage and control. A target with several properties receives every applicable restriction. Custom Definitions can edit the existing immunity arrays but cannot invent a new protection system.

Slow uses the strongest applicable percentage and refreshes its duration. Burn uses the strongest applicable rate and refreshes its duration. Stun refreshes its duration. Reapplication does not add durations or create additive stacks. This declares an adaptation contract; the module does not schedule status ticks or resolve overlapping live actors.

## Profile-defined vocabulary (version 2)

A version 1 Definition fixes the lists above: seven enemy properties, four damage types and targeting modes, Camo detection, and slow, burn and stun. A Definition with `version: "2"` declares them in a `vocabulary` instead, so a Profile can define its own effects. It drops the fixed rules (`detection`, `slowStacking`, `burnStacking`, `stunStacking`, `damageImmunities`, `slowImmune`, `stunImmune`) and keeps the rest. Delivery, the operators, the progression shape and boosts stay fixed; changing those still needs an Engine change.

| Vocabulary list | Entry |
| --- | --- |
| `enemyProperties` | `{id, name, description}`: what an enemy can be, such as Lead or Boss. |
| `bonusDamageProperties` | Optional list of enemy property IDs that attacks may deal [bonus damage](#bonus-damage) against. Absent or empty, no attack deals bonus damage. |
| `damageTypes` | `{id, name, description, ineffectiveAgainst}`: the properties this type cannot damage. |
| `targeting` | `{id, name, description}`: a target priority. |
| `detection` | `{id, name, description}`: a hidden trait, such as Camo. An attack targets a hidden enemy only when it detects every trait the enemy has. A trait is not also an enemy property. |
| `statusEffects` | A status effect, below. |

A status effect has an `id`, `name`, `aliases` (other words a source may use for it), a `kind`, a `description`, a `magnitude` (`{unit, min, max}`, or `null`), `maxSeconds`, `stacking` and `immune` (enemy properties it does not affect). The kinds are:

| Kind | Magnitude | Meaning |
| --- | --- | --- |
| `moveSpeed` | Required; `percent` is at most 100 | Slows movement. |
| `damageOverTime` | Required, in `damage/s` | Damages each second. It is damage of the attack, so the damage type's immunities also block it. |
| `disable` | None | Stops the enemy, like a stun. |
| `damageTaken` | Required | Makes the enemy take more damage. |
| `knockback` | Required, in `times enemy speed` | Moves the enemy back along its path at that multiple of its own speed for the duration. It is control and deals no damage. |
| `custom` | Optional | Any other effect; the Engine only checks its bounds. |

`stacking` is `{maxStacks, refresh, maxMagnitude}`. `refresh` is `reset` (each application resets every stack's duration), `extend` (each application adds duration, not strength) or `independent` (each stack keeps its own duration). `maxMagnitude`, when set, caps the combined magnitude of all stacks, for example a poison that stacks five times but never exceeds 10 damage/s. Validation rejects duplicate or reserved IDs (the Engine's own words, such as `damage` or `splash`), unknown property references, aliases that name two effects, a magnitude on a `disable` effect, a missing one elsewhere except on `custom`, a `knockback` unit other than `times enemy speed`, and a `maxMagnitude` below the minimum magnitude, on an effect without a magnitude or on `extend` stacking, where it has no effect.

A version 2 attack has `detects` (the traits it detects), the six core stats and `statuses`, a list of `{effect, magnitude, seconds}` sorted by effect ID; `magnitude` is absent for an effect without one. Every status needs a positive duration within `maxSeconds` and a magnitude within its bounds. Upgrades change them with `{kind: "status", target: "base", effect, field, operation, value}`, where `field` is `magnitude` or `seconds` and the operations resolve like stats, and `{kind: "detection", target: "base", trait, value}`. A status resolved to zero is removed. The damage type and targeting take vocabulary IDs. The early-identity rule and the capability budget treat each status effect and detection trait as a capability, like slow and Camo.

The metrics measure stacking. A single-stack effect sustains `magnitude × min(1, seconds / interval)`. An `extend` effect gains duration, not strength. A `reset` effect whose duration covers the attack interval reaches `magnitude × maxStacks`; below that it acts once. An `independent` effect holds `magnitude × min(maxStacks, seconds / interval)`. `maxMagnitude` caps the result. Direct damage adds every damage-over-time effect this way; control reports the coverage of each movement, disable, damage-taken and knockback effect. `mechanics.Sustained(effect, status, interval)` computes this value.

### Bonus damage

Bonus damage is an additive +N per hit against enemies with one enemy property, the typed form of a BTD6 class bonus such as Deadly Precision's +50 to Ceramic ([BTD6 reference](BTD6-REFERENCE.md#deliberate-departures-from-btd6)). Only the properties the vocabulary lists in `bonusDamageProperties` accept it. The Default Profile lists Hardened, adapted from the Ceramic tag, and Blimp, adapted from the MOAB-class `Moabs` tag, such as Bionic Boomerang's +1 and MOAB Press's +4 to MOAB-class (SOL-42-02 on #42). They are separate properties, as the two atlas tags are: a Blimp is not Hardened, and each property's bonus is its own.

- **Change.** `{kind: "bonusDamage", target: "base", property, operation: "add", value}` adds a positive value to the bonus against one listed property. Bonus damage only adds, as the cited btd6-atlas modifiers do (SOL-42-01 on #42): `multiply` and `set` fail validation at the change's `operation` with a message that says so. The resolved bonus is the base attack's bonus, zero without one, plus every purchased `add`, so the additions of two paths sum in a crosspath and a purchase never lowers a bonus. In the mechanics wire a tier lists these as `bonusDamage: [{property, operation: "add", value}]`, each one change of the budget. Each change names one property, so a bonus against Hardened never raises the bonus against Blimp. Another property can use the same typed rule when evidence calls for it.
- **Attack.** A resolved attack lists `bonusDamage: [{property, damage}]`, sorted by property; a property without a bonus is left out. An attack without bonus damage writes no `bonusDamage` field, so artifacts saved before it read and hash unchanged. The base attack may list a bonus, each property once.
- **Runtime rule.** For the Consumer: every hit of the attack that deals damage to an enemy with the property, primary, splash and follow-up hits alike, also while the Active Ability runs, deals its damage plus the bonus against that property. An enemy with two listed properties, such as a Consumer enemy marked both Hardened and Blimp, takes both bonuses; the Default does not make a Blimp Hardened, and btd6-atlas cannot confirm the sum ([BTD6 reference](BTD6-REFERENCE.md#deliberate-departures-from-btd6)). The Active Ability's damage multiplier and a follow-up's `damageMultiplier` scale ordinary damage only; the bonus is added per hit. The bonus never overrides an immunity: a hit whose damage type cannot hurt one of the enemy's properties deals no damage, bonus included. Damage over time takes no bonus.
- **Checks.** The property must be listed, the operation `add`, the value positive, the resolved bonus within the stat ceiling, and the attack must deal damage, since the bonus adds to its hits. A bonus with no effect in a legal build, such as one against a property the damage type cannot hurt, fails the no-effect checks. The early-identity rule and the capability budget treat bonus damage against a new property as a new capability, like a new status: it waits for the third purchase under the Default policy, while raising a bonus the base attack already has is allowed earlier. Bonus damage against a new property is also a behavior transition.
- **Plan promise.** When the vocabulary lists a property, plans may promise `bonus-damage`: as an improvement, some listed property's bonus rises in every legal build that contains the purchase; as an unlock, the attack gains a bonus against a property it had none against. `bonus-damage` is a reserved ID.
- **Metrics.** Purchase evidence adds one reading per listed property, `direct damage rate against Hardened` and `direct damage rate against Blimp` under the Default: (damage + bonus against that property) × projectiles ÷ interval plus damage over time the enemy is not immune to, zero when the damage type cannot hurt it. Each reading takes one enemy with only that property, so a Hardened bonus never shows in the Blimp rate. The other rates, the capstone copy bounds and the design policy stay bonus-free.
- **Display.** The unit sheet reads "Adds +50 damage against Hardened enemies (20 to 70 per hit)." and the attack "Each hit deals +50 damage against Hardened enemies (70 per hit)."; a follow-up takes "0.4 times the hit damage (8), plus +50 damage against Hardened enemies" and the Active Ability's sentence adds the bonus unscaled to its boosted damage the same way; a Blimp bonus reads "Adds +4 damage against Blimp enemies" the same way, and one attack with both names each with its own damage per hit. Crosspath rows, kit stats ("Damage against Hardened" and "Damage against Blimp", each shown as +N) and the Profiles tab ("Bonus damage against: Hardened, Blimp") show it too. The review reads `attack.bonusDamage` in `legalBuilds` and fails a purchase that claims a class bonus its resolved builds lack.

Contract version 2 is a separate artifact version. A request, prepared request, draft, checked draft, Result and Profile carry `schemaVersion: "2"` exactly when their Definition is version 2, and each reader chooses the schema from that field. Version 1 artifacts stay readable and resolve as before. `UpgradeDefinition` translates a version 1 Definition into a version 2 one with the same limits; the tests translate every recorded version 1 blueprint and check that validity, metrics and capstone comparisons are identical. The prompts list the vocabulary with IDs, names, aliases, bounds and stacking, so the model maps source wording to an effect or reports it as unsupported.

## Checks and limits

Validation checks all legal builds and every immediately preceding purchase. It rejects nonfinite or invalid stats, nonpositive intervals or ranges, fractional counts, malformed status pairs, area delivery without an area, attacks with no contribution, negative or ineffective boosts, invalid durations, forbidden early activation, missing boost prerequisites, invalid source indices, ineffective upgrades and exceeded Definition limits. Numeric multipliers must be positive. Negative additions are permitted only when every resulting legal build remains valid. Every upgrade must improve at least one supported dimension in every legal build: a larger damage, range, target count, projectile count or control magnitude/duration; a smaller attack interval; new Camo access; or an owned or improved boost. Boost interval multiplier and cooldown improve when reduced, while its other numeric fields improve when increased. Changed damage type, delivery or target priority is accepted as a potentially meaningful qualitative change; a changed volley distribution counts only when the attack fires more than one projectile. A purchase that only reduces or preserves these dimensions is rejected separately from a no-op. A single change that alters no legal build containing its purchase, such as setting a stat to the value it already has, is rejected even when the purchase's other changes have an effect; the changes of one status entry are judged together. Splash radius does not count as a benefit when the resulting pierce remains one, because the primary target already consumes the entire target cap. An increased boost damage multiplier does not count when direct damage remains zero. These guards reject ineffective parameter changes without estimating combat balance. Mixed benefits and drawbacks are allowed; this does not establish that their tradeoff or price is balanced. Values are not rounded or clamped to hide invalid input.

Tier 1 and Tier 2 may introduce at most one new capability group. Splash, slow, burn, stun, Camo, a damage-type change and bonus damage against each property each count as a group; the two fields describing one slow or burn count together. Existing attack parameter improvements can coexist within the structural budget. The bundled policy prohibits new early statuses, delivery patterns, follow-ups, targeting changes and multi-shot patterns; improving existing effects or personal detection remains allowed. The bundled profile gives tiers 3 to 5 a five-change budget. A custom `requireTier3BehaviorChange` policy can additionally require a supported behavior transition; the default permits scalar development. These are editable authoring constraints, not universal BTD6 rules. This check limits explicit behavior additions, but it cannot prove thematic coherence from prose or guarantee that the Unit retains a meaningful weakness.

Reading an artifact checks less than making one. `ValidateTyped` runs every check above and guards each step that makes or checks a unit: drafting, repair, `check` and review. `ValidateStructure` runs only the structural checks: the Definition and blueprint schemas, cost ceilings, source fact references, at least one change per tier, boost placement and multipliers, and valid resolved values in every legal build, including the resolved boost and splash checks. It skips the authoring checks: change budgets, early attack identity and capabilities, purchases with no effect or only drawbacks, single changes with no effect, and the design policy. `render`, `view` and `build` use `ValidateStructure`, so an authoring check added after a Result was saved cannot hide its unit sheet or its builds; the view's `authoringIssues` and `render --details` list the authoring checks it fails today, apart from its stored Findings. A new design judgment belongs with the authoring checks.

The Definition fixes this version's supported arithmetic, scope, readiness and stacking semantics. It exposes a version, identity, revision, label, progression limits, immunity arrays and a Profile containing currency, cost ceilings, a numeric ceiling and complexity budgets, including `earlyTierMaxChanges` through `earlyTierThrough` (1 to 3); omission preserves legacy budgets through tier 3, while the fresh authoring profile explicitly sets 2. Its `balanceStatus` is always `experimental-starter-scale`. The default `btd6-combat-v1` uses Gold, a 10,000 base cost ceiling, 1,000,000 incremental cost and stat ceilings, three changes per tier through tier 3, four changes at tiers 4 and 5, and one new early capability group; the bundled authoring Definition allows three through tier 2 and five from tier 3. A version 2 Definition profile sets `maxChangesPerTier` and `earlyTierMaxChanges` itself, up to 8 each; version 1 keeps at most four and three. These are editable authoring bounds, not calibrated balance targets. Different versions or additional operations require Engine implementation and tests, not prose that claims support.

The mechanics tests cover crosspath inheritance, deterministic arithmetic, all 64 selections, invalid combinations, temporary boosts, target eligibility, version 1 and version 2 equivalence and design-policy gates with native blueprints; the Engine tests run a scripted reference unit (`src/cli/internal/fixture`) through plan, mechanics, repair, check and review. Passing these checks establishes static consistency within the supplied contract. Character fidelity, strategic usefulness, runtime implementation and game-wide balance require separate evidence and review.

The bundled rules document `default-td-profile-v28` holds only the Default Profile's design taste (purchase roles, match rules, private design checks) and its cited scale references. Build codes, build legality, crosspath counts, the Active Ability slot, Engine limits and the output format come from the Definition and the Engine's stage instructions, so a custom Profile receives them too; the plan prompt derives the legality and Active sentences from `progression` and `designPolicy`, and asks that a path's permanent purchases and its Active develop one form, with the Active amplifying what the path already owns. The vocabulary reaches the model once, as `definition.vocabulary` in each stage's context; the stage instructions say only how to use it. The rules document keeps the 1-health enemy layer and the Dart Monkey 0-0-0 reference values of 200 Gold, 1 damage, a 0.95-second interval, 32 range and 2 pierce, with top-path incremental prices of 140, 200, 320, 1,800 and 15,000 Gold. Its purchase roles state the path progression: a third purchase that defines or distinguishes the path, a fourth that develops it and a fifth that is its pinnacle, with Dart Monkey's Triple Shot as a simple identity and Mermonkey's top path (tentacle form, stronger tentacles and an ink slow, then nearby water) as the scale of a full progression. It adds references for more roles and branch scales, each with prices, per-purchase mechanics and a derived comparison: Mermonkey's top path, Dart Monkey's top path (group capacity per throw 2, 5, 36, 120 and 2,250), bottom path (precise damage per second 3.2, about 22 and about 94) and middle path (darts per second and an allied active, whose fourth and fifth prices pay for allies and so must not price or shape a self-only Active Ability), Boomerang Monkey's middle path (frequency, then a 10-second active, then a permanent state with a stronger active), Sniper Monkey's top path (single-target damage and blimp control), Ice Monkey's top path (control persistence, access and uptime), Tack Shooter's middle path (a burst active whose uptime grows from 15 to 45 percent) and Monkey Village (allied support, unsupported here), plus the roster's price bands. These guide proposed values and shapes rather than fixing any character's kit, and no price ratio is used as an output multiplier. The match rules also ask for whole-number damage per hit, as in every reference; that is the Profile's design choice, and code accepts fractions.

Gold is the user's label for BTD6-like cash. Health is the shared player life pool, with a 150-Health starter assumption. Units have no HP. The 1-health layer and life pool are design references; enemy layer trees, leak simulation and runtime durability were not added.

The values are pinned to btd6-atlas capture 56.3, Steam build 24829026, revision `a380413`; the [BTD6 reference](BTD6-REFERENCE.md) lists the tower and upgrade files behind each line and how the comparisons were derived. The retired `btd6_towers.json` package and its page snapshots are no longer cited by any default consumer. Missing values remain unknown.

Before changing defaults, the exact previous Ink ruleset and v3 profile were preserved in the private Towerright checkout at `profiles/unit-generator-ink-v3/`, with `ruleset.json`, `provenance.json` and `README.md`. Public contributors do not need that repository. Existing artifacts and custom Requests retain their explicit Definitions; applying a Profile is an explicit replacement, not an artifact migration.

Count diagnostics identify the resolved value, the starting base and the purchased modifier locations. Generation and repair prompts require positive integer projectile and pierce counts in every intermediate build and crosspath. Fractional multipliers remain supported when the composed counts stay integral; for example, 2 pierce multiplied by 1.5 yields 3, but a crosspath addition of 1 makes that result 4.5 and is rejected. Repair must change the authored upgrade values; the Engine never rounds these results.
